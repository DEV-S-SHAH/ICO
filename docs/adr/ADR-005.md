# ADR-005: Hard Gates on CRITICAL_FIELDS Always Enforced — AGGRESSIVE Mode Decision

**Status**: ACCEPTED  
**Date**: 2026-10-06  
**Decision Makers**: Security Engineer, Architect, Cache Engineer  
**Reviewers**: All Phase 3 Review Agents  

---

## Context

The Phase 3 architecture (PHASE3_ARCHITECTURE.md, Sections 3 and 10) proposes three `GateMode` options for the Decision Engine's hard gate evaluation:

| Mode | Behavior | Threshold |
|------|----------|-----------|
| **STRICT** | All metadata field differences block the hit | 0.95 |
| **BALANCED** | Non-FUZZY field differences block; FUZZY fields allow with confidence penalty | 0.80 |
| **AGGRESSIVE** | **Only CRITICAL_FIELDS block**; all other field differences allow with confidence penalty | **0.65** |

**CRITICAL_FIELDS** (per architecture): `tenant_id`, `model`, `provider`, `entity`, `quarter`, `prompt_version`, `tool_version`, `collection_version`

The SECURITY_REVIEW_PHASE3.md (Sections 15, 18, 20) identifies AGGRESSIVE mode as a **CRITICAL** security risk:

> **AGGRESSIVE MODE IS UNSAFE FOR PRODUCTION USE.**
> - Allows false hits on `topic` (revenue vs margins), `prompt_version`, `tool_version`, `collection_version`
> - Cross-tenant leakage if `tenant_id` gate is bypassed (bug in payload mode filter)
> - Directly violates "Correctness > Hit Rate" principle

---

## Decision

**AGGRESSIVE mode is REMOVED from the Phase 3 architecture.**

Only two gate modes will be supported:

| Mode | Behavior | Threshold | Use Case |
|------|----------|-----------|----------|
| **STRICT** | All metadata field differences block the hit | 0.95 | Regulated, financial, healthcare, multi-tenant production |
| **BALANCED** | Non-FUZZY field differences block; FUZZY fields allow with confidence penalty | 0.80 | Internal tools, single-tenant, non-sensitive workloads |

**AGGRESSIVE mode will not be implemented.** The `GateMode` enum will contain only `STRICT` and `BALANCED`.

---

## Justification

### 1. Security Risk Assessment (SECURITY_REVIEW_PHASE3.md:15)

| Scenario | AGGRESSIVE Result | Impact |
|----------|-------------------|--------|
| Different `topic` (revenue vs margins), same entity/quarter | **FALSE HIT** | Financial misreporting |
| Different `prompt_version`, same model/entity | **FALSE HIT** | Behavioral drift |
| Different `tool_version`, same tool/args | **FALSE HIT** | Tool behavior change ignored |
| Different `collection_version`, same query | **FALSE HIT** | Stale corpus data served |
| Cross-tenant (if tenant_id gate bypassed) | **DATA LEAK** | **CATASTROPHIC** |

### 2. Principle Violation: "Correctness > Hit Rate"

The architecture's core principle (PHASE3_ARCHITECTURE.md:26) states:
> **Correctness > Hit Rate. A wrong cache hit is worse than a cache miss.**

AGGRESSIVE mode explicitly trades correctness for hit rate by lowering the confidence threshold to 0.65 and allowing non-CRITICAL field mismatches. This is a **direct architectural violation**.

### 3. Payload Mode Compound Risk

In `payload` isolation mode (shared collections with `tenant_id` filter), a filter bug could allow cross-tenant vector search. AGGRESSIVE mode would then **not block on `tenant_id` mismatch** because the gate logic only applies to fields present in both incoming and cached metadata — if the filter fails to include `tenant_id`, the gate doesn't see it. STRICT and BALANCED modes would still catch this via other CRITICAL fields, but AGGRESSIVE's reduced gate surface increases blast radius.

### 4. No Valid Production Use Case

The architecture review (PHASE3_ARCHITECTURE_REVIEW.md:129) states:
> **Critical Issue**: AGGRESSIVE mode (0.65 threshold) allows fuzzy gate passes on non-CRITICAL fields, directly violating "Correctness > Hit Rate" principle.

No production workload justifies a 35% false-hit tolerance. Internal tools can use BALANCED (80% threshold) with explicit opt-in.

---

## Consequences

### Positive
- **Eliminates entire class of false hits** from non-CRITICAL field mismatches
- **Simplifies gate logic** — no three-mode branching in hot path
- **Aligns with core principle** — correctness never traded for hit rate
- **Reduces audit surface** — fewer modes to test, document, and monitor

### Negative
- **Lower hit rate** for workloads with frequent non-CRITICAL metadata variation
- **No "maximum reuse" mode** for single-tenant internal experimentation

### Mitigation for Negative
- BALANCED mode with explicit FUZZY field designation provides controlled relaxation
- FUZZY fields must be explicitly declared in `MetadataSchema` (opt-in, not default)
- Single-tenant internal tools can use BALANCED with custom FUZZY fields

---

## Implementation Requirements

1. **`GateMode` enum** in `metadata_guard.py` or new `decision_engine.py`:
   ```python
   class GateMode(str, Enum):
       STRICT = "strict"
       BALANCED = "balanced"
       # AGGRESSIVE = "aggressive"  # REMOVED
   ```

2. **Default mode**: `STRICT` (fail-safe)

3. **Mode selection**: Per-request via `DecisionContext.reuse_policy` (default: STRICT)

4. **FUZZY field declaration**: In `MetadataSchema` per field:
   ```python
   MetadataField(name="topic", field_type=str, required_in_gate=True, fuzzy=False)
   # Only explicitly fuzzy=True fields allow BALANCED pass-through
   ```

5. **Audit logging**: Every BALANCED-mode decision with fuzzy passes logged at WARN level with `gate_mode=BALANCED`, `fuzzy_fields_passed=[...]`

6. **Documentation**: Update PHASE3_ARCHITECTURE.md Section 3 to remove AGGRESSIVE references
